# MERCHROOM — Implementation Plan และแนวคิดโครงการ

## 1. ทำไมจึงทำ MERCHROOM

MERCHROOM เริ่มจากปัญหาที่พบได้จริงของคนรักศิลปิน ดนตรี และงานคราฟต์ไทย: สินค้า Merchandise กระจายอยู่หลายช่องทาง ข้อมูลสินค้าและสต็อกไม่ชัดเจน การค้นหาตามศิลปิน/ประเภททำได้ยาก และงานหัตถกรรมไทยร่วมสมัยมักไม่ได้เล่าเรื่องของผู้สร้างอย่างเพียงพอ

โครงการจึงตั้งใจสร้างร้านค้าออนไลน์ที่รวมสองโลกไว้ด้วยกัน คือ Pop Culture Merchandise และ Thai Heritage Craft โดยให้การเลือกซื้อเป็นประสบการณ์ที่มีเรื่องราว ใช้งานง่าย และข้อมูลการซื้อขายเชื่อถือได้

### อธิบายแบบสั้นที่สุด

MERCHROOM คือ "ห้องรวมของที่แฟนรัก และเรื่องราวที่คนอยากรู้" ลูกค้าไม่จำเป็นต้องไล่หาเสื้อศิลปิน กระเป๋างานคราฟต์ หรือของขวัญจากหลายร้าน ขณะเดียวกันทีมร้านไม่ต้องตอบคำถามราคาและสต็อกจากข้อมูลหลายชุด เพราะทุกคนมองข้อมูลชุดเดียวกันในระบบ

## 2. ภาพที่ต้องการให้เป็น

MERCHROOM ควรเป็นแพลตฟอร์ม e-commerce ที่มีคุณลักษณะต่อไปนี้

- ลูกค้าค้นหาสินค้าตามศิลปิน หมวดหมู่ แท็ก หรือช่วงราคาได้
- ข้อมูลสินค้า ราคา รูปภาพ ตัวเลือก และสต็อกมาจากฐานข้อมูลกลางเดียว
- ลูกค้าจัดการตะกร้า ชำระเงิน และติดตามสถานะคำสั่งซื้อได้
- ผู้ดูแลจัดการสินค้า หมวดหมู่ สต็อก และคำสั่งซื้อแบบใกล้เคียง real time
- การชำระเงินบัตรใช้ Omise โดยสถานะธุรกรรมถูกบันทึกในระบบ
- น้องเห็ดช่วยค้นหาสินค้า เช็กสต็อก แนะนำตามงบ และส่งคำสั่งเพิ่มลงตะกร้า โดยไม่สร้างข้อเท็จจริงขึ้นเอง
- Thai Heritage ไม่ได้เป็นเพียงหมวดสินค้า แต่สื่อคุณค่าของชุมชน ช่างฝีมือ และงานออกแบบร่วมสมัย

### ตัวอย่างประสบการณ์ที่ต้องการ

1. คุณลูกค้าเลือก "Taylor Swift" -> เห็นเฉพาะสินค้าที่มีศิลปินนี้ พร้อมราคา ไซส์ และรูปจริง
2. คุณลูกค้าถามน้องเห็ดว่า "มีของขวัญไม่เกิน 1,000 บาทไหม" -> น้องเห็ดค้นจากฐานข้อมูล ไม่เดาราคา
3. คุณลูกค้าชำระบัตร -> ระบบสร้าง Order, สร้าง Payment, ส่งไป Omise และบันทึกผลกลับมา
4. แอดมินแก้สต็อกสินค้า -> หน้าร้านและ chatbot ใช้ข้อมูลใหม่ ขณะที่ ProductChangeLog เก็บร่องรอยการแก้ไข

## 3. หลักคิดในการออกแบบ

| หลักคิด | การตัดสินใจในระบบ |
|---|---|
| Source of truth เดียว | MongoDB เป็นแหล่งข้อมูลสินค้า สต็อก ออเดอร์ และการชำระเงิน |
| แยกความรับผิดชอบ | React ดูแลประสบการณ์ผู้ใช้, Express ดูแลกติกาธุรกิจ/API, Mongoose ดูแลข้อมูล |
| ปลอดภัยก่อนความสะดวก | cookie สำหรับ session, middleware แยกสิทธิ์ customer/admin, secret อยู่ใน environment |
| สถานะตรวจสอบได้ | Order และ Payment แยกกัน, มี ProductChangeLog สำหรับ audit การเปลี่ยนสินค้า |
| AI ไม่แทนระบบธุรกิจ | Gemini เลือกเรียก tools ได้ แต่ Backend เป็นผู้ query database และยืนยัน action |
| ขยายได้ | Category, Artist, Tag, Image gallery และ API modules แยกออกจากหน้าเว็บ |

## 4. ลำดับการพัฒนาเชิงเหตุผล

### Phase 1 — Define experience และข้อมูลหลัก

1. กำหนดกลุ่มลูกค้า: แฟนศิลปิน ผู้ซื้อของขวัญ และผู้สนใจงานคราฟต์ไทย
2. สร้าง User journey: ค้นหา -> ดูสินค้า -> ตะกร้า -> checkout -> ชำระเงิน -> ติดตามออเดอร์
3. ออกแบบโมเดลข้อมูลก่อน UI ที่ซับซ้อน: User, Artist, Category, Product, Cart, Order, Payment และ Review
4. จัดรูปแบบสินค้าด้วย category, artist, tag, images, imageFit และ quantity เพื่อให้ค้นหา/กรองได้จริง

เหตุผล: หากข้อมูลสินค้าและความสัมพันธ์ไม่ชัดเจน จะทำ filter, dashboard, checkout และ chatbot ที่เชื่อถือไม่ได้ในภายหลัง

**ผลลัพธ์ที่ควรมี:** รายชื่อ entity, ความสัมพันธ์, กติกาสต็อก, สถานะ order/payment และตัวอย่างข้อมูลสำหรับทดสอบ

### Phase 2 — สร้างหน้าร้านและ state ฝั่งลูกค้า

1. พัฒนา React SPA, routes, shared Layout และ design tokens
2. สร้างหน้าร้าน Pop Culture / Thai Heritage / Product Detail
3. ใช้ CartContext ให้ตะกร้าทำงานเหมือนกันทุกหน้า
4. ทำ Auth flow และเส้นทางที่ต้องล็อกอิน เช่น Checkout, Account

เหตุผล: ผู้ใช้ต้องเห็นคุณค่าและเส้นทางซื้อสินค้าจบก่อน แล้วจึงเชื่อมระบบธุรกิจที่ต้องการความถูกต้องสูง

**ผลลัพธ์ที่ควรมี:** หน้าเว็บใช้ได้บนหลายขนาดจอ, route ชัดเจน, cart ไม่หายเมื่อเปลี่ยนหน้า และ protected pages ป้องกันผู้ที่ยังไม่ login

### Phase 3 — เชื่อม Frontend, Backend และ Database

1. เพิ่ม REST routes และ controllers สำหรับ auth, catalog, cart, orders, categories, reviews และ admin
2. ให้ Product/Category/Artist เป็นข้อมูล live จาก MongoDB
3. เพิ่ม admin workflow สำหรับเพิ่ม/แก้ไข/ลบสินค้า หมวดหมู่ แท็ก รูปหลายรูป และ image fit
4. ย้ายการตัดสินใจสำคัญ เช่น ราคา สต็อก และสถานะ order ไปอยู่ฝั่ง server

เหตุผล: ลดข้อมูลซ้ำใน client และป้องกันการแก้ราคา/สต็อกจาก browser โดยตรง

**ผลลัพธ์ที่ควรมี:** ทุกหน้าสำคัญเรียก API, admin แก้ข้อมูลได้, การเปลี่ยนข้อมูลถูกบันทึก และ frontend ไม่เป็นแหล่งความจริงของราคา/สต็อก

### Phase 4 — Checkout และ Payment ที่ตรวจสอบได้

1. สร้าง Order จากรายการสินค้าในตะกร้าและ snapshot ราคา ณ เวลาซื้อ
2. ตรวจสต็อกและลดจำนวนอย่างควบคุมได้ใน backend
3. สร้าง Payment แยกจาก Order เพื่อเก็บ provider, status, charge id และข้อผิดพลาด
4. เชื่อม Omise: token/charge/webhook และอัปเดต order-payment ตามผลจริง
5. แจ้งการเปลี่ยนสถานะ order ผ่าน SSE ให้ลูกค้าและผู้ดูแลเห็นเร็วขึ้น

เหตุผล: การชำระเงินเป็นธุรกรรมที่ต้องแยกสถานะให้ตรวจสอบย้อนหลังได้ และต้องไม่เชื่อสถานะจาก frontend เพียงอย่างเดียว

**ผลลัพธ์ที่ควรมี:** ออเดอร์ไม่สำเร็จจะไม่ถูกแสดงว่า paid, payment ที่ล้มเหลวมีเหตุผลให้ตรวจสอบ, และ webhook อัปเดตสถานะได้

### Phase 5 — Agentic AI Shopping Assistant

1. ให้ Gemini รับผิดชอบความเข้าใจภาษาธรรมชาติและเลือกใช้เครื่องมือ
2. ให้ backend tools ค้นสินค้า ตรวจรายละเอียด เช็ก stock แนะนำตามงบ และเตรียม cart action
3. จำกัด agent ให้ตอบเฉพาะ facts ที่เครื่องมือส่งกลับ ไม่สร้างราคา/ส่วนลด/สต็อกเอง
4. จำกัด rate, จำกัดความยาวข้อความ, เก็บ API key ไว้ server-side และมี fallback model

เหตุผล: AI ช่วยให้ค้นหาสินค้าสะดวกขึ้น แต่การเข้าถึงฐานข้อมูลและ action ต้องอยู่ภายใต้กติกาของระบบ ไม่ใช่ให้ LLM เขียนข้อมูลโดยตรง

**ผลลัพธ์ที่ควรมี:** น้องเห็ดอ้างอิงข้อมูลจริง, ไม่แต่งราคา/สต็อก, จำกัดการใช้งาน API และแจ้งผู้ใช้อย่างสุภาพเมื่อ Gemini quota ไม่พอ

## 5. Definition of Done ของระบบ

- ลูกค้าซื้อสินค้าด้วยข้อมูลราคาและสต็อกจริงจากฐานข้อมูล
- ผู้ดูแลเห็นออเดอร์พร้อมวันที่/เวลา และอัปเดต catalog ได้
- Payment มีสถานะตรวจสอบได้จาก Order และ Payment record
- น้องเห็ดตอบด้วยข้อมูล current จาก database หรือแจ้งเมื่อไม่มีข้อมูล
- UI ไม่เปลี่ยนเพราะการเพิ่ม capability ของ backend
- มี ER Diagram และ Architecture Diagram อ้างอิงโค้ดปัจจุบันสำหรับทีมพัฒนาต่อ

## 6. ขอบเขตที่ควรพัฒนาต่อ

1. ทำ Cart ให้ agent เขียนผ่าน authenticated server cart ได้แทน client-side cart action
2. เพิ่ม schema สำหรับ ProductVariant หาก size/สีมี stock แยกกัน
3. เพิ่ม OrderPromoCode/discount snapshot หากต้องใช้โค้ดส่วนลดกับออเดอร์จริง
4. เพิ่ม unique index สำหรับ Review (userId + productId) หากต้องการหนึ่งรีวิวต่อหนึ่งสินค้า/ผู้ใช้
5. ใช้ queue หรือ idempotency key สำหรับ webhook และ stock reservation เพื่อรองรับ concurrent checkout
